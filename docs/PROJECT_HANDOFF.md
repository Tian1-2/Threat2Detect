# Threat2Detect 项目开发交接文档（讨论稿）

更新：2026-11-01。给四名组员及各自的 AI 使用。本文区分**已对齐的方向**与**待组长确认的实现选择**；未确认项不能被开发者自行扩大为项目承诺。首个 Agent 原型及实测结果见 `docs/POC_RUNBOOK.md`、`docs/BASELINE_REVIEW.md`。

## 1. 一句话目标

先阅读**整篇**新威胁报告，把其中有检测意义的行为转成有原文依据的 ATT&CK 映射，并给每项行为标注可能需要的日志源；再选择可用日志支持的一部分行为，检索并分析 Sigma 规则对**具体做法**的覆盖、执行样例验证。最终报告同时展示完整的行为视图与局部验证边界。候选 Sigma 规则生成可作为独立模块提前开发；主流程调用它时再核对实际缺口。

这不是“从企业全部日志中自动发现未知入侵”的 SIEM，也不是“每篇报告都自动生成一条新规则”。ATT&CK 技术标签是检索与组织线索，不能代替规则条件分析。

## 2. 第一版范围与成功标准

| 项目 | 第一版约定 |
|---|---|
| 报告输入 | 优先用自带 ATT&CK 映射的 CISA 报告：AA25-266A、AA23-319A 为开发案例，AA24-193A 红队演练报告为封存测试；**整篇提取**有检测意义的行为，保留出处、原文位置与事实强度。原先 `docs/GOLDEN_REPORTS_FULL.md` 的 Unit 42 报告保留作无官方答案的探索案例 |
| ATT&CK | 为报告中证据足够的行为提出映射；不明确的保留 `unmapped`/`uncertain`。其中选择约 2–3 个技术进入首版规则执行演示，而非只分析这 2–3 个技术 |
| 日志 | Windows Sysmon 为唯一必需事件源；优先使用本地 OTRF 数据，按需加入另一份独立公开样本或少量**明确标注为合成**的良性事件 |
| 规则库 | 官方 [SigmaHQ/sigma](https://github.com/SigmaHQ/sigma) 为正式基库；先固定少量相关规则及版本，不把全库直接投入运行 |
| 执行环境 | 本地 Python，**必须实际运行所选 Sigma 规则对静态 Sysmon 事件的匹配**；不接真实 SIEM；第一版不需要 MCP |
| 新规则 | **不是验收必需项**。组长可用人工指定的行为、字段和样本独立开发生成模块，不依赖成员 B；主流程只在具体检测缺口、字段可观测且测试范围写清楚时调用，输出“候选规则”，不宣称生产可用 |
| 演示成功 | 输入报告后，系统给出原文证据、技术映射、规则条件与字段核对、样例测试结果、未覆盖及不确定项；人工能复查每个结论 |

当前已有材料：`docs/FIRST_SCENARIO.md`（手工案例）、`tools/inspect_dataset.py`（OTRF 事件摘要）、`tools/check_lsass_rule.py`（一条规则的手工条件核对）。后者不是通用 Sigma 引擎。

## 3. 必须保持清楚的证据边界

每个结论拆成两个维度，不使用一个模糊的“已覆盖”标签：

1. **整篇行为清单**：每项写事实/推测、ATT&CK 候选、可能需要的日志源、当前是否具备验证数据。超出 Sysmon 的行为仍保留；用 `not_evaluated`/`insufficient_telemetry` 表示未验证。
2. **所选行为的规则分析**：`matches_procedure` / `partially_matches` / `does_not_match` / `insufficient_detail`。依据是报告的具体行为描述与 Sigma 检测条件。
3. **样例日志的运行结果**：`hit` / `miss` / `not_tested` / `incompatible_logsource`。依据是具体事件 ID、字段值和规则运行记录。

报告不必附有原始日志。OTRF 样本不等于报告中的真实事件。若报告使用 Task Manager 转储 LSASS，而 OTRF 使用 Dumpert，即使二者同属 T1003.001，也只能说规则在 Dumpert 样例上的运行结果；对 Task Manager 的覆盖必须另行分析或验证。

测试证据等级：

- **合成匹配事件**：验证解析和匹配器能运行，不能证明检测效果。合成良性事件可做明确边界检查，不能据此估计真实误报率。
- **独立公开攻击日志**：在固定规则后测试，能证明对该样例命中或未命中。来自同一数据生产者的多个场景可增加多样性，但不等同于完全独立的生产环境验证。
- **真实良性环境日志与不同攻击实现**：才能较可信地讨论噪声、漏报和规则松紧。第一版若没有，只报告“未评估”，不编造数字。

## 4. 整体架构

```text
整篇威胁报告 ──> 全篇行为提取 ──> ATT&CK 检索/核对
                                  │
                                  v
                        日志需求/可观测性盘点
                                  │
             ┌────────────────────┴────────────────────┐
             v                                         v
    有样本的行为：Sigma 检索/分析               无样本的行为：保留映射与需求
             │                                         │
     日志适配/字段标准化                         标明未验证范围
             │
             v
     本地规则执行/样例验证
             │
             v
     结论汇总：证据、命中、缺口、限制、候选规则
```

**主控 Agent** 保存状态并决定是否继续检索、执行验证、请求人工复核或停止并标注证据不足。LLM 用于理解报告和提出有依据的映射/覆盖判断；YAML 解析、字段映射、布尔条件执行、ID 校验和结果计数由确定性代码完成。工具有结构化输入输出，不能把自由文本直接当成已验证事实。MCP 只是未来暴露工具的一种接口选择，第一版用普通 Python 函数即可。

## 5. 模块接口（先冻结，后并行开发）

模块之间用 UTF-8 JSON 兼容的对象传值。所有 ID 稳定、可追溯；字段缺失用 `null` 或明确状态，不得猜填。**准确字段名、枚举、A→B 交接点与验证命令以 `docs/INTERFACE_CONTRACT.md` v1.0 为准**。下表只说明职责；不得根据旧实验 JSON 自行另定接口。

| 模块/函数 | 输入 | 输出及责任 |
|---|---|---|
| `extract_behaviors(report)` | `case_handoff.report` 与无答案输入文本 | 更新 `case_handoff.behaviors[]`，原文引句/位置和 `fact_status` 必填；不得按当前日志类型预先丢弃攻击行为 |
| `map_attack(behaviors, catalog)` | `behaviors[]`、固定版本 ATT&CK 目录 | 更新 `case_handoff.mappings[]`；一个行为允许多条技术映射；无证据时不造 ID |
| `assess_observability(...)` | 全篇行为、技术映射、数据清单 | 更新 `case_handoff.telemetry[]`；先判断需要什么证据，再选本地可测试行为 |
| `search_rules(...)` | 确认的行为与映射、固定 SigmaHQ commit | `rule_candidates`；tag 仅用于召回，记录规则路径、哈希和真实字段条件 |
| `assess_coverage(...)` | 行为证据、完整规则 YAML | `coverage_assessments`；逐条件判断具体做法，不能只凭 ATT&CK tag |
| `normalize_events(dataset)` | OTRF 路径、数据集说明 | `normalized_events`；保留原始位置及解析失败数 |
| `evaluate_rule(rule, events)` | 规则 YAML、标准化事件 | `rule_tests`；实际执行规则，保留命中事件 ID 与不支持语法 |
| `generate_rule(request)` | 组长人工指定的检测目标、字段与样本 | `rule_generation_result`；独立于成员 B 的规则检索模块开发 |
| `build_report(...)` | 各阶段结构化结果 | 人可读报告 + `case_result`；每项结论能回到原文、规则文件和事件 ID |

成员 A/B 的人工判定方法见 `docs/REVIEW_PROTOCOL.md`，可填写的样例见 `data/annotations/`。4 条行为级黄金行已确认；B 的 4 条报告覆盖示范已确认，OTRF 事件条件样本已确认。A/B 按各自样本调优。候选规则生成模块可用人工指定的场景单独开发；与 SigmaHQ 的重复/缺口核对只在集成展示时进行。

`evaluate_rule` **必须执行规则**，不是只让 LLM 阅读 YAML 后猜测命中。静态 JSON 可以逐条重放：先把事件字段标准化，再解析所选 Sigma YAML 的 `logsource`、`detection`、修饰符和 `condition`，逐条求值并返回命中事件 ID。先支持第一版实际选中规则所需的语法（如 `contains`、`startswith`、`endswith`、`all`、`and/or/not`）。遇到不支持的规则必须返回 `unsupported_rule`，不能当成未命中。若使用 pySigma，先确认它承担的是规则解析/转换；本地 JSON 匹配仍需合适执行器或自写的受限实现。字段标准化时特别注意：本地 OTRF 一些 Sysmon 字段位于 `Message` 文本中，不能直接按顶层键匹配。

## 6. 黄金案例与验收

**当前以 AA25-266A 的 4 条独立人工行为标注为起步黄金样本**，本地无答案输入及参考 ID 见 `docs/POC_RUNBOOK.md`；AA24-193A 是授权红队演练，需与真实事件分开报告。`docs/GOLDEN_REPORTS_FULL.md` 保留先前对 Unit 42 报告的全篇人工候选清单，`docs/GOLDEN_REPORTS.md` 保留首版 Sysmon 教学选段。组长已确认 4 条行为级映射；4 条规则覆盖示范已复核，A/B 分别用它们调优；再选约 2–3 个有本地数据的技术做规则执行。测试日志优先使用本地 OTRF `LSASS_campaign_06`（Dumpert）。不同来源、不同做法的边界必须写清；不把样例结果冒充报告中真实事件的检测结果。

黄金案例文件由人工分两层写：**全篇行为与 ATT&CK 清单**（含不确定项及所需日志），以及**所选行为的规则/事件验证答案**（至少两条候选规则的适用与不适用原因、OTRF 关键事件 ID、预期结果和局限）。开发时用它检查模块接口和推理质量；不要把黄金答案硬编码进提示词或检索器。若加入第二个 OTRF 场景，先确认其数据和标签实际存在，再把它留作**未参与规则编写的独立样例**。

验收时必须能展示：

- 原文行为与映射理由可追溯；事实与推测分开。
- 报告的其余有检测意义行为仍出现在清单中，即使日志源超出 Sysmon；给出所需日志及未验证原因。
- 同一 ATT&CK 技术下，能指出至少一条“标签相关但具体条件不覆盖”的规则。
- 一条兼容规则可在 OTRF 事件上给出可复核的命中；不兼容和语法未支持有单独状态。
- 样例验证、静态覆盖判断、误报未知这三类信息不混写。
- 候选新规则如出现，说明相比现有规则新增的检测目标、预期误报来源和验证等级。

## 7. 四人分工（按工作量不平均分配）

| 人员 | 主责 | 明确交付与接口 |
|---|---|---|
| **组长／你：主控与集成（大头）** | 定范围、冻结接口、主控 Agent 状态与分支、模块集成、最终报告、验收；可独立开发候选规则生成与验证模块 | `run_case` 入口、统一数据模型、结果汇总、端到端演示；审核所有“覆盖/有效”表述 |
| **成员 A：报告理解与 ATT&CK** | 按组长确认的行为级黄金行调优报告切分、行为提取、事实/推测区分与候选检索；提交新增争议行供组长裁决 | `extract_behaviors`、`map_attack`；每轮错误清单、提示词/检索版本与改进证据 |
| **成员 B：Sigma 检索与规则分析** | 用已复核覆盖判定与 OTRF 事件样本优化规则索引、条件解析和具体做法覆盖分析；争议行交组长确认；与组长协作确定本地执行器支持范围 | `search_rules`、`assess_coverage`；候选规则列表、逐条件理由与争议清单；不可只按 tags 判断 |
| **成员 C：轻量任务** | 整理 OTRF 样本说明、整理少量攻击相关/背景候选事件、核对字段表、维护黄金案例和运行说明；不承担主控或规则引擎 | 数据清单、`dataset_id`/事件证据表、可复现运行步骤；标明合成数据与真实数据 |

考虑到成员 C 的其他作业较重，其任务应有清晰边界，预计明显少于其他人。组长可接管本地规则执行/字段标准化的主要开发，或在组内按实际能力将其中一小段交给成员 B；**接口负责人仍为组长**，避免无人负责集成。

## 8. 协作与防止并行开发错位

1. 先由组长发布本文件、统一模型/接口和黄金案例初稿；各人把文档交给自己的 AI，并明确“按本文契约开发，不自行扩大范围”。
2. 每人先交付一个能用黄金案例运行的最小函数与输入输出样例，再扩展实现。不得各自发明不同的 ATT&CK ID、字段名或结论枚举。
3. 规则库固定 commit 或 release，并在结果里记录；不能让不同成员在不同版本上讨论同一规则。
4. 模块发现接口冲突、缺失日志、报告语义不清或规则语法超出支持范围时，立即带着**具体输入、期望输出和影响**找组长确认。组长负责更新契约并同步所有人。
5. 候选规则和验证结论需要人工复核后才能进入最终展示。不得让 Agent 把“未测试”改写成“通过”。

## 9. 实现边界与后续数据需求

下列选择不阻塞 A/B 按已固定接口开发；组长在本地规则执行阶段按实际规则语法确定具体实现。

已确认：CISA 映射表只用于盲标后的报告级对照，不进入行为级黄金理由；开发集与封存测试集分开；必须实际运行所选规则；候选新规则不是必需项；ATT&CK 固定 Enterprise v20.0，详见 `docs/DATA_VERSIONS.md`。SigmaHQ commit 已固定为 `05d1031f537e830b76da53bae2400c5814c89165`。

1. **本地执行器范围**：只实现选中规则需要的 Sigma 子集，还是接入支持本地事件的现成执行器？默认先调查现成方案，再按实际规则最小实现；不承诺完整 Sigma 兼容。
2. **独立良性样本来源**：现有 OTRF 活动日志包含已复核的背景候选事件，可练规则条件，但没有逐事件良性真值。若最终要报告误报率，需要额外取得带可靠来源与上下文的独立良性日志；未取得前只报告样本上的具体误命中风险，不报总体误报率。

## 10. 给每位组员 AI 的统一开场指令

> 请先阅读仓库根目录 `README.md`、`READING_GUIDE.md`、`docs/TEAM_START.md`，再按自己角色阅读其中指向的材料。你负责本文件第 7 节分配给我的模块。先复述你的输入输出契约、依赖和待确认问题，再给出最小可运行实现；保留报告原文、规则路径与事件 ID 的证据链。不要把 ATT&CK 标签当成规则覆盖结论，不要声称合成日志可证明真实误报率。遇到契约冲突，请提出具体问题交给组长确认。
