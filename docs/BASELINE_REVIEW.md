## 已确认的错误类型

- `ipconfig` 被映到 `T1049`（网络连接发现），而 CISA 表将网络配置检查列为 `T1016`。模型抓住“网络”一词，忽略了命令作用。
- `tasklist` 被映到 `T1059.001` 或泛化的 `T1059`，漏掉 CISA 原标 `T1057`（进程发现）。
- `fscan` 至少一处被映到 `T1595.001`；应结合报告中它扫描内部服务的上下文与 CISA 表的 `T1046` 复核。
- `Stowaway` 被映到 Windows 服务建立或远程访问工具；CISA 报告说明它用于连接代理，原表为 `T1090`。只看工具名会误判用途。
- 同一命令列表中的路径和命令被拆成几十条；部分映射理由与最后给出的 ID 自相矛盾。这些是模型判断错误，不能用程序的 ID 合法性校验掩盖。

## 一次小范围调优实验

提示词 `poc-2` 要求把同一行动里的工具和目的合并。单句“使用 PowerShell 和 bitsadmin 下载载荷”的试验从 3 条碎片降为 1 条，但模型只给了 `T1059.001`，没有给下载动作的 `T1105`。对 509 字的命令列表片段仍提取 22 条，未改善列表过度拆分。由此可见，单靠这次提示词修改无法解决问题。

`poc-2` 又在修正后的完整输入 `data/reports/cisa-aa25-266a-input.txt` 上运行，结果见 `data/runs/cisa-aa25-266a-prediction-v2.json` 和 `data/runs/cisa-aa25-266a-evaluation-v2.json`：7 个分段，约 395 秒，提取 89 项行为；官方 22 个 ID 找到 14 个，漏 8 个，额外 22 个 ID 待审。这与首轮使用的输入范围不同，**不能把 15/22 与 14/22 当作纯提示词 A/B 测试**。程序校验全部保留引句的位置与 ID 合法性通过。

新版输入保留了映射表之后的缓解建议和事件时间线。抽查发现第 6 段中的 12 项均是面向防守方的建议，虽然模型多数给了空 ID，却仍把它们放进攻击行为清单。第 7 段也有把建议性描述和时间线标签当成攻击行为的情况。后续应在送入提取器前按章节过滤**防守建议**，同时保留真正的攻击时间线，并给过滤结果留出处。

## 下一轮应做什么

1. 为少量段落人工标注 **行为边界 + 可接受的技术 ID**，与 CISA 报告级表形成两层答案。先挑 `ipconfig`、`tasklist`、`fscan`、`Stowaway` 及几项推测/尝试，便于定位错误发生在提取还是映射。
2. 将命令列表识别为一个“列表块”，按动作类别归并；允许同一行为对应多个 ATT&CK 技术，并要求每个技术有独立理由。不能通过把官方 ID 写进提示词来提高分数。
3. 改善候选技术检索，记录正确 ID 是否进入候选集；对未召回与模型选错分别计数。必要时试更强的本地模型或用户选择的付费接口。
4. 用开发集 AA23-319A 检查改动的可迁移性；最终再打开封存的 AA24-193A。之后才进入 Sigma 规则条件分析和 OTRF 日志执行。
